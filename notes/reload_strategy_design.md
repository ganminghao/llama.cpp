# Reload 策略设计

## 1. 当前的 Reload 策略设计思路思路

> 2025年10月16日16:59:22

### 1.1 Reload 替换策略和执行解耦

- 修改 `GGML_MAX_SRC = 20`，合并为一个算子，但是仍然调用三个函数：

1. `sparkinfer_reload_plan()` **<-- Reload 策略变更时，只有这个函数需要被修改！**
2. `sparkinfer_reload_evict()`
3. `sparkinfer_reload_exec()`

- 我们甚至可以写多个函数，比如：
  - `sparkinfer_reload_plan_by_dfr()`
  - `sparkinfer_reload_plan_by_lru()`
  - `sparkinfer_reload_plan_by_fifo()`
  - `sparkinfer_reload_plan_by_opt()`
  - `sparkinfer_reload_plan_by_clock()`
  - `sparkinfer_reload_plan_by_nru()`
- 然后用 `sparkinfer_reload_plan()` 来调用其中一个。
- 这样的设计，保证了我们可以随时切换 Reload 策略以测试其替换效果和时间开销。

> ### 为什么 Reload 策略和 Evict 策略不需要分开？
> 
> 因为在始终保证 GPU Cache 全满的情况下，Evict 策略是不可能存在的————当你确定了哪些组需要被 Reload 之后，哪些组需要被 Evict 也就同步确定了。

### 1.2 操作系统中的替换策略参考

- 参考了：《操作系统（第3版）》5.3.4 页面替换策略，「1. 驻留集固定的替换策略」，共 5 种。

> ### 🌱 为什么不参考「2. 驻留集可变的替换策略」呢？
> 
> - 根据我的思考，在我们的 SparkInfer 项目里面，「每个 layer 的 GPU Cache 的容量」是固定的，并不会随着 decode 过程中 activation pattern 的变化而变化。
> - 因为与操作系统可以同时监测所有线程的资源消耗不同，我们的 Predictor 是 layer-wise 的，只有等上一层的 Attention + LayerNorm 输出之后，才能用这个结果去预测这一层的 FFN activation pattern。
> - 我们不具备同时 predict 所有 layer 的 activation pattern 的能力，也不具备同时调整所有 layer 的 Cache 大小的能力。

1. FIFO（First In First Out）：略
2. OPT（OPTional replacement）：OPT策略是驻留集大小固定这类策略中的最优策略。（// [YPX] [C] 但不一定是 SparkInfer 的最优策略？）它淘汰下次访问距当前最远的那些页中序号最小的一页。称OPT为驻留集固定类策略中的最优策略的理由是，OPT策略对任意一个访问串的控制均有最小的时空积（进程所占空间与时间的乘积）。
3. LRU（Least Recently Used）：略
4. CLOCK：CLOCK策略是一种基于LRU思想的简化算法。页表项需要增加一个访问位，硬件访问页面时置上访问位，进程所有驻留页形成一个类似钟面的环形链表，有一指针指向当前欲淘汰页。当需要淘汰页面时，如果指针指向的页访问位是0，则将其淘汰，指针顺时针方向转一格；如果指针指向的页访问位是1，则将访问位清0，指针顺时针方向转一格，……，直到找到访问位是0的页，将其淘汰。该算法既考虑了最近被访问的因素，清除访问位代价也较小，是一种比LRU更实用的算法。
5. NRU（Not Recently Used）：每页设表示其被使用的访用位，每访问一页就置对应的访用位为1，页管理软件则定时地把所有的访用位重新置0。当必须淘汰页时，任选一访用位为0（可能不唯一，但表明该页最近没有被访问）的页。若所有页的访用位都为1，则按FIFO规则淘汰。
6. 关于「工作集（Working Set）」：工作集是一种驻留集可变的替换策略。在不考虑驻留集大小变化的情况下，其使用的替换算法是：用计数器记录对各页的访问，经自动检查后淘汰计数器值为Δ的页。由于实现WS策略耗费太大，故实际系统中很少采用。一般来说，系统中会使用一种叫 SWS（Sampled Working Set）的变体，策略为：在WS策略的控制下，每过τ个时间单位（如取τ＝10000）检查一次计数器，将计数器值大于等于Δ的页淘汰。这样做耗费仍很大，可用硬件时钟计数来进一步降低耗费。每访问一页，同时将当前时钟值记录在页表项中，经τ时间单位后便检查驻留集，将当前时钟值与记录在页表项中的值相减，淘汰差值大于等于Δ的页。还有一个叫 VMIN 的改版，没怎么看懂。

> ### ✨ Gemini 的建议
> 
> #### 关于“操作系统页面替换策略”的借鉴
> 
> 你对驻留集固定与可变策略的分析非常到位。确实，在 SparkInfer 的场景下，每个 Transformer Layer 的 FFN Cache 大小是预先分配好的，是固定的。我们不具备全局视角去动态调整所有 Layer 的 Cache，因此聚焦于驻留集固定的替换策略是完全正确的方向。
> 
> 接下来，我们深入探讨一下你提到的几种策略在 SparkInfer 场景下的适用性：
> 
> - OPT (Optimal)：你敏锐地指出了“它不一定是 SparkInfer 的最优策略”，这非常正确。操作系统的 OPT 策略是理论最优，因为它假设能预知未来所有的页面访问序列。在我们的场景中，"未来"就是后续 Token 解码时将被激活的神经元。我们的 Predictor 正是在做这件事，但它只是“预测”，不是“预知”，必然存在误差。因此，我们追求的应该是一个基于预测结果的、现实可行的最优策略。
> - LRU (Least Recently Used)：LRU 的核心思想是“最近使用过的，将来也很可能被使用”，这与神经元激活的时间局部性是吻合的。但其主要问题在于实现开销较大，需要为每个 Cache 块维护一个时间戳或在链表中频繁移动节点，在要求极致性能的推理场景下，这个开销可能需要仔细评估。
> - CLOCK & NRU (Not Recently Used)：这两个是 LRU 的高效近似。特别是 CLOCK 算法，只需要一个额外的访问位和环形指针，开销非常小，非常适合在性能敏感的系统中使用。NRU 定时清零访问位的思想也很有趣，相当于在一个时间窗口内观察神经元分组的“热度”。考虑到 llama.cpp 和 GGML 追求极致性能的风格，CLOCK 或 NRU 可能是你初步实现时的绝佳选择。
> 
> #### 跳出“通用策略”，思考“领域特定策略”
> 操作系统策略是通用的，但我们的场景是高度领域特定的。我们最大的优势在于拥有一个神经元激活预测器。我们可以设计一个与预测器紧密结合的、更主动的替换策略。
> 
> 我构思了一个 “预测感知的分级替换策略” (Predictor-Aware Hierarchical Eviction Strategy)，供你参考：
> 当 Cache 不足需要替换时，我们可以将被缓存的神经元分组（Neuron Groups）分为三个优先级：
> 
> - P0 (不可替换): 经由 Predictor 预测，在当前这次推理中将被激活的神经元分组。这是最宝贵的资产，绝对不能被换出。
> - P1 (次优先): 未被本次预测，但在历史上（例如，最近N个Token）被频繁激活的神经元分组（即 PowerInfer 所谓的 "Hot Neurons"）。这些是潜在的热点，我们倾向于保留它们。（// [YPX] [C] 可能具有参考价值，因为甘明昊说「layer GPU Cache 的容量」和 「被激活的神经元数量」谁大谁小是没有定论的）
> - P2 (最低优先级): 未被本次预测，且历史上也未被频繁激活的神经元分组 ("Cold Neurons")。
> 
> 替换逻辑：
> 
> 1. 首先从 P2 级别的分组中进行淘汰。淘汰P2内部的分组时，可以采用简单的 FIFO 策略（谁先进来谁先走），因为它们的优先级已经最低了，无需再为它们精细计算。
> 2. 如果淘汰完所有 P2 之后空间仍然不足，再从 P1 级别的分组中进行淘汰。同样，内部可以使用 FIFO 或 LRU。
> 3. P0 级别的分组永远不会被选为牺牲者。
这个策略的核心优势在于，它将预测的先验知识和历史的统计信息结合了起来，比单纯依赖历史访问的 LRU/CLOCK 更具前瞻性。这与 SparkInfer 结合 PowerInfer 稀疏预测机制的思路也是一脉相承的。
>
